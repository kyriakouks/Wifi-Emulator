# Lightweight 802.11aa Groupcast Guide

This guide explains the group-addressed delivery mechanisms implemented in
`main.py`, the relationship to IEEE 802.11aa, and the deliberate simplifications.

## Purpose

IEEE 802.11aa adds MAC enhancements for robust audio/video streaming. One of
its important areas is reliable group-addressed delivery: sending one stream
from an AP to multiple associated stations while improving on legacy multicast,
which normally has no receiver acknowledgements and no retry mechanism.

`main.py` is deliberately scoped to make that difference easy to observe. It
compares:

1. Legacy multicast
2. GCR Unsolicited Retry
3. A lightweight GCR Block Ack feedback model

It does **not** try to reproduce every normative 802.11aa frame field or PHY
interaction.

## Fixed topology and timing

```text
                         AP
                         |
       ----------------------------------------
       |                 |                    |
     STA-1             STA-2                STA-3 ... STA-4

  Every AP <-> station frame crosses a fixed 5 ms one-way medium delay.
```

The topology is fixed:

- `AP` sends each group DATA frame to `STA-1`, `STA-2`, `STA-3`, and `STA-4`.
- Every AP-to-station DATA frame arrives after `MEDIUM_DELAY_S = 0.005`.
- Every station-to-AP Block Ack feedback frame also arrives after exactly 5 ms.
- The `5 ms` value never varies by station, category, or retry attempt.

Frame airtime and SIFS are used only to prevent simulated frames from
overlapping in the event schedule. They are not computed from a PHY rate.

## Mode 1: Legacy multicast

```text
AP                                      Group members
|---- GROUP DATA ----------------------> STA-1 ... STA-4
|              fixed 5 ms delay
|
+---- no acknowledgement and no retry
```

Implemented in `handle_receive_group_data()` when the active mode is
`GroupcastMode.LEGACY`.

Characteristics:

- AP sends exactly one group DATA frame per group packet.
- Stations that miss that copy remain missing.
- AP receives no receiver feedback.
- Lowest control and transmission overhead.
- Lowest reliability when receiver misses exist.

## Mode 2: GCR Unsolicited Retry

```text
AP                                      Group members
|---- GROUP DATA copy 1 ---------------> STA-1 ... STA-4
|---- GROUP DATA copy 2 ---------------> STA-1 ... STA-4
|---- GROUP DATA copy N ---------------> STA-1 ... STA-4
|
+---- no receiver feedback
```

Implemented in `handle_unsolicited_retry()`.

Characteristics:

- AP sends `1 + --gcr-retries` group DATA copies.
- The retry count is fixed; the AP does not know whether stations received any
  prior copy.
- A station discards a later copy if it already accepted the same sequence.
- More copies can improve the chance that a member eventually receives the
  packet.
- It may send unnecessary copies when every member received an earlier copy.

This captures the key GCR Unsolicited Retry trade-off: robustness without a
feedback exchange.

## Mode 3: Lightweight GCR Block Ack

```text
AP                                      Group members
|---- GROUP DATA ----------------------> STA-1 ... STA-4
|              fixed 5 ms delay
|<--- Block Ack report ----------------- each receiver that has the packet
|              fixed 5 ms delay
|
+---- aggregate reports
      |-- all members acknowledged -> complete
      `-- one or more missing -> retransmit group DATA, up to retry limit
```

The model is implemented through these methods:

- `schedule_block_ack_window()` creates a serialized feedback window.
- `handle_receive_block_ack()` records a member's feedback at the AP.
- `handle_block_ack_window_complete()` chooses completion or retransmission.

Characteristics:

- Stations that have received a sequence produce a simplified Block Ack report.
- The AP aggregates reports into `packet.acknowledged_by`.
- The AP retransmits only if a group member is not represented in the feedback.
- Stations ignore duplicate DATA copies after their first successful receipt.
- Feedback has a cost: additional Block Ack frames use the medium and each
  frame has the same fixed 5 ms delay.

### Important abstraction

Actual IEEE 802.11aa GCR Block Ack includes detailed rules for control frames,
acknowledgement policy, group membership, sequence spaces, and receiver
coordination. The simulator does not reproduce those frame formats or timing
rules. Instead, it uses one serialized feedback report per newly successful
receiver and an AP aggregate acknowledgement set. This makes the key
feedback-driven retransmission decision visible without adding a PHY or
control-frame collision model.

## Deterministic abstract receiver misses

No radio propagation calculation exists in this simulator. To compare delivery
methods, a receiver can miss a DATA copy through an abstract input controlled
by `--receiver-miss-probability`.

For each combination of:

```text
seed + packet sequence + station + DATA copy number
```

`main.py` derives one repeatable outcome with SHA-256. The result:

- is independent of physical distance and all PHY properties;
- is identical when compared modes send the same packet copy to the same
  station; and
- allows reproducible comparisons from one run to the next.

For example, if `STA-2` misses packet 3's first DATA copy under `legacy`, it
will also miss that same first copy under both GCR modes. GCR modes may then
send extra copies, giving `STA-2` additional independent opportunities to
receive the packet.

Set `--receiver-miss-probability 0` to turn this input off entirely.

## EDCA-style queueing

Packets are assigned a deterministic pseudo-random category from:

```text
voice > video > best-effort > background
```

The AP maintains one FIFO queue per category. `dequeue_highest_priority_packet`
selects the front packet of the highest-priority non-empty queue, while
`begin_edca_access` adds category-specific AIFS and CWmin backoff delay.

This is intentionally a **scheduler**, not a complete EDCA implementation:

- There is one transmitting AP, so no AP/AP contention is modeled.
- There are no separate virtual stations or virtual collisions within the AP.
- Backoff counters do not decrement/freeze slot-by-slot.

The queueing exists to show that groupcast reliability works alongside
priority-labelled stream traffic; it should not be used to evaluate EDCA
performance or fairness.

## Relationship to 802.11aa theory

The simulation demonstrates the following 802.11aa-relevant idea:

> Groupcast delivery can improve robustness over legacy multicast either by
> transmitting a predetermined number of copies without feedback or by using
> receiver feedback to drive retransmissions.

It does **not** implement these other 802.11aa areas:

- Normative GCR management and Block Ack frame procedures
- Stream Classification Service (SCS)
- Intra-access-category stream prioritization and drop precedence
- Overlapping BSS mechanisms
- 802.1Q/AVB stream-reservation interworking
- Full EDCA, DCF, RTS/CTS, NAV, or unicast ACK state machines
- PHY, rate control, aggregation, power save, or radio propagation behavior

This scope is intentional: the simulator is a teaching and comparison tool for
groupcast reliability behavior, not an IEEE conformance simulator.
